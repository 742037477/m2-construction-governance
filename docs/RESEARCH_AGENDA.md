# 研究议题与复现回报

这个参考实现希望让“Agent 是否受治理”变成可以检查输入、状态、效果和证据的问题。欢迎从一个小范围、可复现、可证伪的主张开始，提交失败案例、对照实验、适用边界或实现改进。当前没有声称社区独立复现已经成功，也不把样例完成等同于方法在任意任务上有效。

先读 [设计](DESIGN.md)、[配置](CONFIGURATION.md) 与 [复现步骤](REPRODUCING.md)。本仓库供许可范围内的学习与研究，商业使用另行授权；它不采用“公开源码即无限使用”的表述。

## 可以从哪些问题开始

| 议题 | 可检验的问题 | 建议的最小对照 | 应保留的证据与边界 |
|---|---|---|---|
| 范围表达与实际门控 | 用户约束中哪些能被 Scope 准确表示，哪些仍只能由人审？ | 同一候选下，授权内请求与只改变一个越界字段的请求 | 原 Scope、请求差异、拒绝原因、实际文件效果；不能以拒绝次数代替语义正确率 |
| 崩溃与 UNKNOWN 恢复 | 中断前后是否保留操作身份，恢复是否避免重复效果？ | 独立研究环境中固定同一请求，在不同阶段中断并核实 | 意图、日志、原 ID、文件与账本状态；未确认效果保持 UNKNOWN |
| 长任务的约束连续性 | 换会话或进程后，目标、预算、候选与未决项是否丢失？ | 同一任务材料下比较仅摘要与按原件恢复；预先列明不可丢约束 | 阶段/attempt/检查点、来源 head、恢复前后差异；只归纳实际任务长度与条件 |
| 项目知识的证据级别 | 宿主是否把草稿、旧报告或冲突材料误升为事实？ | 保持目标相同，只改变来源 claim_type、哈希或显式冲突 | context 输出和宿主实际结论；加载器正确不等于模型正确使用 |
| 失败经验的适用性 | 相关变更能否排除旧经验，无关变更是否造成不必要失效？ | 固定原失败，只改变一项相关依赖或一项无关文件 | 历史锚、依赖指纹、纳入/排除原因、新任务绑定；不继承旧授权 |
| 候选与被测对象一致性 | 测试工具读到的字节是否就是冻结候选？ | 同一用例比较候选目录与外部构建路径，明确实际依赖 | argv/cwd、Maven `-f` 等路径、被跟踪文件、产物和回执；不自动假定全依赖已覆盖 |
| 独立审查质量 | 有效签名之后，业务结论是否仍可能错？ | 预先标注的有限用例，由真实分离的作者/审查者处理 | 候选、测试范围、review 及逐项纠错；不同指纹不等于认知独立 |
| 状态与完整性信任 | 哪些修改能被现有校验检测，哪些依赖外部可信锚？ | 在可丢弃副本中改变单项材料，并明确攻击者权限 | 变更前后哈希、外部锚、实际拒绝；不能把本地哈希链说成不可篡改日志 |
| 跨平台语义 | 路径、链接、大小写、进程和编码差异是否影响同一约束？ | 固定运行时代码和输入，记录 Windows/macOS/Linux 差异 | OS/Python/依赖、命令、输出与跳过原因；平台未运行就写未运行 |
| 宿主接线与隔离 | 真正进入受控入口的效果占哪些，绕行路径由谁控制？ | 显式列出一个宿主的工具/资源入口及其权限部署 | 实际调用轨迹、ACL/容器等部署证据；当前 Python 包没有全局拦截器或 OS 沙箱 |

表中内容是研究建议，不是已实现的测试套件、预先证实的结论或新运行授权。实验应限定在自己有权操作的隔离对象；对源码的变化应作为独立派生版本记录。

## 如何让结论具有因果解释力

1. 先选明确主张，例如“当已登记来源字节改变时，读取器排除其内容”，不要把目标写成笼统“系统可靠”。固定版本与预期观察。
2. 选择可信原版作为对照，固定输入、前置操作、对话历史、数据范围与必要配置。不能固定的因素列出；不要拿正在修改的候选作基准。
3. 每次改变一个与主张相关的条件。先留原失败，再定位首个可证差异；不要连续加补丁后只展示最终成功。
4. 涉及模型随机性时，预先说明模型、提示、上下文、参数与有限复测次数。程序 Gate 的确定性结果和模型自然语言判断分开报告。
5. 列出反例、替代解释与未覆盖条件。两版都复现时先考虑原有缺陷；两版都未复现时只报告本轮未复现。
6. 修复后重复同一最短真实流程及必要影响检查。不要用大量无关组件测试掩盖关键用户路径没有执行。

可测量拒绝是否正确、证据是否充分、恢复是否一致、重复效果是否发生、审查误报/漏报及资料错误升级等。测量口径、分母和人工标注依据必须公开；若另研究耗时或 token 开销，应明确那是新问题，不是原版本已宣称的接受条件。

## 贡献可以从小范围开始

- 文档：指出一个与实际接口不一致的字段、命令或状态含义，并给出源码位置。
- 复现：提供一个平台、一个固定版本、一个步骤清楚的结果，包括不成功的结果。
- 机制研究：给出当前边界内的反例或能区分两种解释的对照。
- 实现改进：保留原版本和失败证据，说明最小 diff、受影响接口与验证范围。
- 宿主适配：公开实际接线、角色映射、信任锚与绕行边界，避免只展示提示词或演示录像。

通过仓库提供的讨论、问题或贡献渠道回报；具体接收规则以仓库当前贡献说明为准。不要提交私钥、凭据、个人业务数据、可重放的生产授权或未经许可的第三方材料。

## 复现回报模板

复制以下模板，未执行的项目写 `NOT_RUN`，未知写明原因。无需为了填写模板追加无关测试。

```markdown
# 复现标题

## 研究问题与版本
- 要检验的具体主张：
- 原版发行物/commit 与 SHA256：
- 候选改动标识或 diff（无改动写明）：
- 许可范围内的使用场景：

## 环境与信任前提
- OS、架构、Python、cryptography：
- 模型/宿主及参数（未调用模型写 NOT_RUN）：
- 项目知识配置 schema、来源清单与适用条件：
- bootstrap 等级、配置哈希与可信锚取得方式：
- 实际权限/隔离与可能绕过入口的路径：

## 输入、步骤与对照
- 输入与初始候选哈希：
- 前置操作、cwd、命令、对话历史：
- 对照中唯一变化，以及无法固定的条件：
- 预期输出/效果（执行前定义）：
- 实际输出、退出码和实际文件/状态效果：
- 实际复测次数与各次结果：

## 证据与范围
- 操作 ID、task/revision、freeze/candidate、回执及日志索引：
- 测试实际覆盖，NOT_RUN 与未覆盖项：
- 累计预算、原失败、UNKNOWN 与未决记录是否保留：
- 独审、CEO、PRE、release、POST、人工审阅分别到哪一步：
- 原证据可访问方式，公开材料删减/脱敏范围：

## 判断与下一步
- 已证实事实：
- 推断及其支持证据：
- 未知、替代解释和限制：
- 最小修复建议与同条件复核结果（如有）：
```

回报中的“通过”必须带对象和阶段。`STARTUP_READY`、`CONTEXT_READY_FOR_REVIEW`、CONFIG_3、TEST、review、PRE 和 POST 不是同一种结论，见 [状态说明](../runtime/docs/STATUS_MEANING.md)。真实签名或内容哈希不能替代业务事实核查。

已有 Windows 限定记录可用作起点，不能作为社区独立复现结果引用。macOS/Linux、其他模型与外部项目需要各自真实记录；研究结果也不能自动赋予本项目人工 PASS。
